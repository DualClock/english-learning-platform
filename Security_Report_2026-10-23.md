## 3. Что исправлено

### 3.1. F-1 · AI-гейт: `GET /api/books/{id}/parallel` тратил Gemini без подтверждённого email

**Где было:** `Controllers/BooksController.cs:378` — у класса только
`[Authorize]`, а `GetParallelPage` вызывает `TranslateChunksAsync` →
`AiService.TranslateLiteraryAsync` (`:413`) и `TranslateTextAsync` (`:434`) →
один платный вызов на страницу книги. `[RequireConfirmedEmail]` стоял на четырёх
контроллерах (`AiController`, `AssistantController`, `AudioController`,
`PronunciationController`), и «страхующий» тест `RegistrationAndAiQuotaTests.cs`
перебировал ровно эти четыре типа руками — то есть BooksController был для него
невидем в принципе.

**Почему критично:** регистрация открыта, письмо подтверждается по клику,
значит disposable-аккаунт мог листать параллельный перевод любых загруженных
книг и списывать бюджет провайдера; это ровно тот сценарий, ради которого гейт
и ставился (A01 + A04, деньги).

**RED (до фикса):**

```
AiCostGateCoverageTests.BooksController_ParallelTranslationEndpoint_RequiresConfirmedEmail [FAIL]
AiCostGateCoverageTests.EveryAiBackedAction_IsGatedOrExplicitlyListedAsAiFree [FAIL]
  Assert.Empty() Failure: Collection was not empty
  Collection: ["BooksController.GetParallelPage"]
```

**Фикс:** `[RequireConfirmedEmail]` на действии
(`Controllers/BooksController.cs:379`) — только на него, чтобы читалка,
словарь и прогресс остались доступны неподтверждённым.

**Тест вместо списка контроллеров.** Новый `AiCostGateCoverageTests` не
перечисляет «AI-контроллеры» руками: он собирает инвентарь из конструкторов —
контроллер считается способным потратить деньги, если получает `AiService`,
`AssistantService`, `SpeechService` или `ResilientAiService`. Каждое его
действие обязано либо нести гейт, либо стоять в обозримом списке
«Gemini не трогает». Первый же прогон этого теста поймал мою собственную опечатку
в списке (`BooksController.DeleteBookmark`), так что механизм работает в обе
стороны. Отдельный тест сверяет сам инвентарь — иначе при переименовании
сервиса проверка молча перестала бы что-либо проверять.

**GREEN:** 3/3 теста зелёные, полный прогон 216/216.

### 3.2. F-2 · AI: появился лимит частоты на пользователя в минуту

**Где было:** ни на одном AI-эндпоинте не было `[EnableRateLimiting]`
(политики живут только на `auth`, `signup`, `admin`, `feedback`, `upload`,
`analytics`). Единственный тормоз — `AiQuotaService`: дневные счётчики читаются
из Postgres и кэшируются на 60 секунд (`Services/AiQuotaService.cs:92-96`), а
проверка и запись не атомарны (`ResilientAiService.cs:85-101` проверка,
`:242-251` запись после ответа).

**Почему критично:** 300 вызовов в день на аккаунт можно выбрать параллельным
всплеском за секунды, пока кэш показывает «0», — а на глобальном бюджете в
2000 вызовов это 15% дневного расхода одним скриптом.

**Фикс:** бронь одного слота на пользователя в текущей минуте UTC
(`AiQuotaService.TryReservePerMinuteRequest`, `:82`) прямо в единственной точке,
где уходят деньги — `ResilientAiService.SendAsync:112`, сразу после глобального
бюджета и дневной квоты, до сетевого вызова. Отказ — новый
`AiRateLimitExceededException` (`ResilientAiService.cs:33`), который
`GlobalExceptionHandler.cs:58` превращает в 429 с `Retry-After: 60`.
Лимит — `Ai:PerMinuteUserRequestLimit`, по умолчанию 30, продублирован в
`appsettings.json` и `render.yaml` (не молчаливый дефолт, на который ругался
R-08).

**Почему не `[EnableRateLimiting("ai")]`:** `UseRateLimiter` стоит в конвейере
до `UseAuthentication` (`Program.cs:256` против `258`), поэтому в момент
лимитинга `context.User` пуст, а `RemoteIpAddress` — адрес прокси (R-02 не
закрыт). Партиция по IP дала бы ровно ту же планетарную корзину, из-за которой
закрыли `signup`; партиция по `sub` из незащищённого заголовка `Authorization`
позволила бы печатать корзины пачками. Проверка на `userId`, уже проверенном
`[Authorize]`, этого лишена. Заодно она покрывает транзитивные пути — тот же
перевод страниц из F-1, куда атрибут лимитера всё равно не дотянулся бы.

**RED и чувствительность тестов.** В статически типизированном коде тест на
новый API не скомпилируется «до», поэтому проверку чувствительности делал
вживую: реализацию оставил, а саму защиту временно отключил
(`TryReservePerMinuteRequest → return true`) и получил три падения:

```
AiRateLimitTests.PerMinuteBudget_DeniesTheBurstBeyondTheLimit [FAIL]
AiRateLimitTests.PerMinuteBudget_IsCountedPerUser [FAIL]
AiRateLimitTests.ResilientAiService_PerMinuteBudgetExhausted_RefusesBeforeCallingProvider [FAIL]
```

После восстановления защиты — 5/5 зелёные, включая assertion на то, что
транспорт провайдера вызван ровно `limit` раз и ни разу сверх.

**Что честно остаётся:** счётчик живёт в памяти процесса, поэтому на N
репликах эффективный лимит ≈ N × 30/мин (Render free — одна, плюс счётчик
спекается рестартом; дневной бюджет по Postgres от этого не зависит). Окно
фиксированное, значит на границе минуты теоретически проходит до 2× лимита.
Системные вызовы с `userId == null` частотой не ограничены — за них отвечает
глобальный бюджет. Мёртвый путь `AiService.GenerateJsonAsync` (`:309`) не
проверяется ни на что: вызовов у него в репозитории нет, так что дыры он не
образует.

### 3.3. F-3 · admin: корзина лимитера перестала быть общей на весь мир

**Где было:** политика `admin` партицировалась через
`RateLimitPartitionKeys.Identity` = sha256(IP + email из тела). Админские
запросы поля `email` не содержат, а GET-тела вообще не читаются
(`RateLimitPartitionKeys.cs:33-36` в прежней версии), поэтому 5 эндпоинтов
(`AnalyticsController.cs:130` и `:175`, `CategoriesController.cs:178`,
`FeedbackController.cs:148`, `GrammarController.cs:33`,
`WordListsController.cs:103`) падали в одну константную партицию. Пока
`Proxy__TrustedCidrs` не настроен, «IP» — адрес прокси, то есть корзина
10 запросов / 5 минут одна на всех.

**Почему критично:** в день релиза любой вошедший пользователь мог в цикле
дёрнуть `/api/feedback` или `/api/analytics/acquisition` и закрыть владельцу
доступ к почте беты и к сидам контента — A04/A07 на стороне Availability, по
цене ровно ноль для атакующего.

**RED (до фикса):**

```
AdminPartitionIsolationTests.Admin_KeyHolder_HasItsOwnBucket_AnonymousFloodCannotEmptyIt [FAIL]
  «флуд без ключа не должен отрезать владельца ключа от админских эндпоинтов»
AdminPartitionIsolationTests.Admin_DifferentKeyValues_GetSeparateBuckets [FAIL]
```

**Фикс:** `RateLimitPartitionKeys.AdminIdentity` (`:58`) — запрос с
`X-Seed-Key` получает корзину, производную от sha256 значения ключа (само
секретное значение в ключ партиции не попадает, это отдельный тест), запрос без
ключа — корзину по IP. `AdminPartition` (`RateLimitPolicies.cs:76`) использует
её; `auth`/`signup` не тронуты.

**Заменённый существующий тест:** `AdminPolicy_PartitionsByIpPlusLoginLikeAuth`
утверждал ровно этот дефект (`Assert.NotEqual` на двух разных email в теле
POST-запроса) — аудит назвал это «дефект зафиксирован как ожидаемое поведение».
Тест переписан на новый инвариант: партиция игнорирует тело, ключ даёт корзину
`key:…`, без ключа — `ip:…`.

**GREEN:** 4/4 изоляционных теста + переписанный, полный прогон 216/216.
